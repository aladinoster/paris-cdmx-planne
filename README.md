# Todo contigo · meetplan

Made for Laura (Mexico City) and Andrés (Paris). An exact optimiser for a long-distance couple's year of trips: **when** to meet, **where** (Paris, Mexico City or a
city in between) and **for how long**. It stays within both people's leave and blocked dates, and trades days together
against fares, hotels and long gaps apart.

- **Web app** (no install, runs in the browser): https://aladinoster.github.io/paris-cdmx-planne/
  · in Spanish: https://aladinoster.github.io/paris-cdmx-planne/#es (EN/ES switch at the top right)
- **Python package** `meetplan`: the same model as a CLI and library, managed with [uv](https://docs.astral.sh/uv/).

Both implementations give identical results; `tests/` checks this.

## Commands

| Command | What it does |
|---|---|
| `uv run meetplan solve` | Optimal plan for the config's scenario |
| `uv run meetplan solve --mode home` | Override the scenario: `home`, `both` or `meet` |
| `uv run meetplan solve --fare-scale 1.1` | Re-solve with every fare 10% higher |
| `uv run meetplan solve -o plan.ics` | Also export the plan: `.ics` (calendar), `.csv` or `.json` |
| `uv run meetplan solve --basis cautious` | Plan with `low` (cheapest seen), `typical` (default) or `cautious` fares |
| `uv run meetplan compare` | Solve the three scenarios side by side |
| `uv run meetplan risk` | Re-plan with low / typical / cautious fares and give each plan's Monte Carlo cost range |
| `uv run meetplan frontier` | Days-vs-cost trade-off: the optimal plan for each value of a day together |
| `uv run meetplan data` | Summarise the fare database (`data/fares.csv`) |
| `uv run meetplan where 9` | Rank every place to meet for a 10-night trip from 15 September |
| `uv run meetplan fares` | Who should fly each month (home trips) |
| `uv run meetplan add-quote --source kiwi --direction PAR-MEX …` | Append one observed fare to `data/fares.csv` |
| `uv run meetplan refresh` | Rebuild `data/fare_model.json` from the fare database and print what changed |
| `uv run meetplan build-web` | Build `docs/index.html` from `web/` and the data |
| `uv run meetplan -c my.toml solve` | Use another input file |

Scenarios: **home** = free trips only to Paris or Mexico City; **both** = home or a third city;
**meet** = third cities only. Fixed trips always keep their own `where`.

Import `plan.ics` into Google Calendar, Apple Calendar or Outlook to get one all-day event per trip.

### As a library

```python
from meetplan import load_config, solve

cfg = load_config("config/2027.toml").with_(mode="home", leave_her=25)
plan = solve(cfg).plan
print(plan.days_together, plan.travel_cost)
for t in plan.trips:
    print(t.s, t.e, t.where, t.leave_me, t.leave_her)
```

## Input data (`config/2027.toml`)

Everything the model knows lives in one commented TOML file. Copy it (e.g. `config/2028.toml`), edit it and pass it
with `-c`.

| Section | Meaning |
|---|---|
| `year`, `mode` | Planning year; default scenario (`home` / `both` / `meet`) |
| `[names]` | Display names: `me` (Paris side), `her` (Mexico side) |
| `[leave]` | Annual leave days for each |
| `[trips]` | `min_days` / `max_days` for free trips, `min_gap` between trips, `max_gap` search window |
| `[value]` | `day`: € value of a day together; `host_working_factor`: value when the host works; `travel_day_factor`; `trip_overhead` €; `gap_target` and `gap_lambda` for the gap penalty; `cost_weight` (how much a euro counts, 0.6 = time first); `meet_cost_factor` (third-city cost counts ×0.7: an effort we choose to make); `trip_bonus` € per trip (frequency) |
| `[focus]` | `month` (1–12): make sure one trip spends at least half its days in that month (default April); optional `where` |
| `[her_constraints]` | Month turn: no leave on her `last_working_days` (1) of a month nor her `first_working_days` (3) of the next, counted in her working days so weekends are skipped; `block_august`; `extra_blackout` dates |
| `[holidays]` | Public holidays per side; these days cost no leave |
| `[fares]` | `scale`, weekend surcharges, the two daily fare `curve`s (Paris→CDMX, CDMX→Paris), the `quotes` they were calibrated on |
| `[[fixed_trips]]` | Trips that must happen. `start` and `end` are `[earliest, latest]`; `where` is `me`, `her`, `home`, `meet:<city>`, `meet:any` or `anywhere` |
| `[[cities]]` | Third-city options: reference fares from each side (`ref_me`, `ref_her`), optional `seen = { 4 = { me = 84, her = 682 } }` (lowest fare observed in a month, overrides the estimate), `lodging` € per night for two, `bonus` € of extra value per holiday day, `enabled`. Includes Barcelona, Madrid, Málaga, Rome and Milan |

### The fare database (`data/fares.csv`)

Every price the model uses comes from real searches, stored one row per quote: when it was checked, the source
(`kiwi`, `lastminute`, `letsfg`), direction, dates, kind (`best_in_month` = cheapest departure day in a month,
`fixed_dates`, `best_in_window` = cheapest pair in a flexible window), the cheapest price, the cheapest nonstop
when known, carriers and notes. The first collection (20 Nov 2026) holds 42 quotes; a second (21 Nov) adds April
fares and the European meeting cities (Barcelona, Rome, Milan, Málaga, Madrid); LetsFG searches aggregate
450–620 offers each, Google Flights included. Expedia and eDreams did not return machine-readable prices.

Findings: on identical dates the three sites differed by ~7%; the cheapest nonstop costs ×1.00–×1.69 the cheapest
fare (median ×1.13); Laura's direction is usually €100–250 cheaper (Air Canada via Montréal, €731–810 in Apr–May
and Aug–Oct); Andrés's dips to €835–850 in mid-May and mid-September (British Airways via London).

To add data, append rows and update the curves in `config/2027.toml`; a test fails if a curve is ever above the
cheapest quote of its month.

### Price uncertainty

Each month's curve value is the **lowest** fare seen. A ticket actually bought is modelled as
`lowest × m`, `m ~ Triangular(1.00, 1.08, 1.30)` (`[fares] band_*`). The optimiser plans with `basis` =
`low` (×1.00), `typical` (expected value, ×1.13, default) or `cautious` (90th percentile, ×1.22), and
`meetplan.prices.simulate_cost` redraws every ticket 4,000 times to give the P10–P90 travel cost.

```
$ uv run meetplan risk
Plan with fares     Days  Trips  Cost (plan)      P10      P50      P90
low                   99      7        8,882    9,523    9,711    9,908
typical               99      7        9,716    9,523    9,711    9,908
cautious              99      7       10,322    9,523    9,711    9,908
```

With money weighted at 60%, the plan no longer depends on catching the lowest fare: all three bases agree.

### Keeping prices fresh

There is one source of truth: `config/2027.toml` (parameters and seed curves) plus `data/fares.csv` (observations).
Everything else is generated:

```
fares.csv ──meetplan refresh──▶ fare_model.json ─┐
2027.toml ───────────────────────────────────────┼─meetplan build-web─▶ docs/index.html ──GitHub Actions──▶ gh-pages
web/page.html + web/solver.js ───────────────────┘
```

- `refresh`: for each curve segment, the lowest fare of the **latest survey** (quotes checked within 45 days of the
  newest one). A newer survey replaces an older one even if it is dearer, so prices can go up as well as down.
  Segments without any quote keep the seed value from the TOML (holiday peaks, months not on sale yet). For third
  cities, it gives the lowest fare per departure month, which overrides the seasonal estimate.
- A **monthly scheduled task** (a Claude session on the 1st of each month) follows [REFRESH.md](REFRESH.md): it
  searches the fares in `config/searches.toml`, appends them with `add-quote`, runs `refresh`, the tests and
  `build-web`, then pushes to `main`. The workflow publishes the page, which shows the date of the newest quote.
- By hand: `fares.scale` (or `--fare-scale`) scales every fare; edit a seed segment or a city's `ref_me` / `ref_her`
  if a season or city has no data.

## The model

A candidate trip is a start day `s`, an end day `e`, a place and, for home trips, whether the host also takes leave.

- **Value:** `V` € per day together; × `β` on days the host works; × `travel_day_factor` on the first and last day;
  plus the city's `bonus` per day for third-city trips.
- **Cost:** the fares (one ticket for home trips, two for a third city), hotel nights (third city only) and a fixed
  `trip_overhead`. In the objective it is multiplied by `cost_weight` (and by `meet_cost_factor` for a third city);
  reported costs are always the real ones.
- **Frequency:** every trip adds `trip_bonus` €.
- **Leave:** the traveller spends leave on each of their working days. The host does too if they take leave.
  In a third city, both do. Her leave is never allowed on her blocked days: her last working day of each month,
  her first three of the next (weekends and holidays skipped), August and any `extra_blackout` date.
- **Focus month:** with `[focus] month = 4`, one extra required trip must start in April and spend at least half of its
  days there.
- **Gaps:** a gap of `g` days apart (including before the first trip and after the last) costs
  `λ · max(0, g − gap_target)²`, so the plan spreads out.

The objective is total value minus costs minus gap penalties, under both leave budgets, the fixed trips and the minimum
gap. It is solved **exactly** by dynamic programming over days with state
`(day, next fixed trip, your leave left, her leave left)`; the two leave dimensions are numpy arrays, so a full year
solves in under a second. `tests/test_solver.py::test_dp_is_optimal_against_brute_force` checks optimality against
exhaustive enumeration on a small instance.

### Web app

`docs/index.html` is a single self-contained page: the same solver in JavaScript (`web/solver.js`), the interface
(`web/page.html`) and the data, injected by `meetplan build-web`. Edit `web/`, never `docs/index.html`. GitHub Pages
serves the `gh-pages` branch, which the workflow rewrites on every push to `main`. `tests/test_web.py` runs the page's
solver in Node and checks it gives exactly the Python plans. The page loads Google Fonts and nothing else. Settings you change on the page are
kept in your browser only.
